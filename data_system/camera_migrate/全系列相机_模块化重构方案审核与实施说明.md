## 1. 覆盖范围和不可越过的架构边界

本方案中的“两个项目”是代码树，不是两个相机型号：

| 项目代码树 | 当前正式产品型号 | 硬件平台 / HAL |
|---|---|---|
| AR 系列项目 `camera2d-rk3588` | AR950、AR940、AR760、AR765 | AR950 为 RK3588；AR940 为 RK3576；AR760、AR765 为 RV1126B |
| D 系列项目 `safety-double-rk3588` | D940、D950、D955 | D940 为 RK3576；D950、D955 为 RK3588 平台族，D955 另有 MCU/PWM 板级差异 |

以上清单以当前顶层构建和打包入口为准。EX950、AR750、D850 等名称虽然可能出现在历史文件或共享前端特性集中，但不是当前顶层构建入口明确接受的正式目标；若产品确认仍需交付，应加入产品清单和验收矩阵，不需要复制一套服务架构。

本次重构覆盖所有型号共同使用的芯片无关部分：

- HTTP、WSS、TCP、MQTT、RTSP/WHEP 等对外协议的身份入口与 Action 映射。
- Action Catalog、Dispatcher、统一错误、审计和事件目录。
- 用户、用户组、Session、API Key 和模块权限。
- 方案、配置、AI、媒体、文件、通信等服务契约。
- 共享 Web UI 与外部算法和相机管理平台的契约。

本次不重写芯片、传感器和板级实现。以下差异继续留在 HAL 或产品硬件 Profile：

- ISP、VI/VPSS/VENC、RGA、RKNN 和厂商 SDK 调用。
- 传感器、IQ、分辨率、帧率和硬件编码能力。
- GPIO/PWM/LED、UART/RS485 设备节点和有效电平。
- 文件系统布局、启动脚本、固件打包与板级恢复。

目标约束是：新增型号只增加 HAL / 产品硬件 Profile 和 capability 数据，不复制 HTTP、WSS、Action、权限或平台 Block 契约。当前代码中仍有少量平台宏、型号常量和板级判断泄漏到共享代码，这些应在触达相应路径时收回适配边界，但不扩大成本轮 HAL 全面重写。

品牌、语言和客户发行包是第三个独立维度。它们可以影响界面资源和启用的产品能力，但不能产生另一套 moduleId、Action、用户组或 API Key 实现。

## 2. 先给结论

你的三期思路是合理的，而且比一次性重写整个相机框架更适合当前团队：

1. 第一期先治理散乱接口，建立统一 Action 和协议边界。
2. 第二期在同一 Action 入口上增加用户组模块权限和 API Key。
3. 第三期再把相机能力整理成稳定服务，供外部 Python 低代码平台组合 Block。

需要做四点修正：

- 第一期不是把所有 HTTP、WebSocket、TCP 代码推倒重写，而是先建立统一入口，再让旧接口逐批接入。
- 第一期必须预留 Principal、moduleId、PolicyGate 和审计钩子，否则第二期还要再次改每个接口。
- 模块目录现在就要定义，模块运行时和大规模 HAL 重构可以放到第三期。
- 平台 Python Block 在逻辑分层上属于外部应用层；即使 DE-2 将获准执行体部署到相机 `blockd`，也不因此进入相机 AI 服务层。断网仍须工作的安全报警、硬实时触发、GPO 失效安全和设备自保护不能全部搬到平台。

最终允许关系很简单：

~~~text
允许调用 =
    当前固件注册了该模块
    AND 当前 HAL / 产品硬件 Profile 满足模块所需能力
    AND 身份有效
    AND 当前主体是 Administrator
        或其用户组启用了该模块
~~~

Administrator 固定拥有本型号的全部功能。自定义用户组按功能模块勾选，新建时默认勾选全部可委派模块；API Key 只绑定一个用户组并继承相同权限。

## 3. 本轮改造做什么、不做什么

### 3.1 要做

- 盘点两个项目代码树面向全部正式型号的外部入口。
- 给每个业务动作分配稳定的 actionId。
- 给每个 Action 映射一个或多个 moduleId。
- 统一身份、错误、审计和业务语义。
- 明确 HTTPS、WSS、TCP、MQTT、RTSP/WHEP、文件传输和内部 IPC 的职责。
- 保留旧接口兼容层，逐批迁移。
- 扩展现有用户管理，支持自定义用户组和模块复选框。
- API Key 绑定用户组，供第三方平台和无界面客户端使用。
- 建立全型号能力矩阵，并把产品型号、硬件平台和发行变体分开。

### 3.2 暂时不做

- 本总计划前两期和 DeepEdge 的 DE-1 不做相机内 Python Block 运行时；如进入 DeepEdge DE-2，只允许在独立受控的 `blockd` 进程运行签名应用包，不把 Python、动态代码或任意 DAG 装入 `camera` 进程。
- 不做厂家侧功能启用或商业功能分级。
- 不建设覆盖全部设备配置的通用事务引擎、事件溯源或复杂工作流引擎；DeepEdge DE-1 只为“方案部署”建立局部 `validate/stage/activate/rollback` 状态机。
- 不要求所有命令都异步 operation 化；升级、模型导入、长时间评测和需要停—写—启/回滚的方案部署使用 operation，其余短命令保持同步。
- 不强迫视频、文件和控制命令使用同一种协议。
- 不一次性重写全部 HAL 和驱动。

## 4. 目标架构：只增加一条清晰主链

~~~text
Web UI / 第三方平台 / SDK / 运维客户端
                    |
        HTTPS / WSS / TCP / MQTT / 媒体协议
                    |
        协议适配器与身份解析
                    |
     Action Catalog + PolicyGate + Audit
                    |
             Action Dispatcher
                    |
              相机服务层
                    |
              HAL / 驱动层
~~~

这里统一的是身份、权限、Action、错误、审计和业务含义，不是把所有流量塞到一个端口。

每个协议入口只负责四件事：

1. 解析请求和身份。
2. 转换成标准 Action。
3. 调用同一个 Dispatcher。
4. 把统一结果转换成协议响应。

业务实现不再关心请求来自 HTTP、WSS 还是 TCP。

## 5. 协议职责

| 通道 | 主要用途 | 不应继续承担 |
|---|---|---|
| HTTPS | 查询、短命令、配置读写、用户组、API Key、创建长任务、文件元数据 | 高频视频帧、持续事件广播 |
| WSS | 已认证事件订阅、状态变化、报警、长任务进度 | 暴露完整配置、继续增加 major/minor 命令分支 |
| MQTT over TLS | 相机主动连接公司平台、desired 通知、reported 状态、离线消息 | 匿名 Broker 指令、直接调用未登记旧命令 |
| RTSP / WHEP / WebRTC | 实时媒体数据面 | 用户管理、系统配置、固件管理 |
| Artifact HTTPS | 模型、固件、Web UI 包、日志导出、图片和录像文件 | 低延迟控制 |
| TCP 6002 / SDK 9000 | 有明确客户依赖的兼容或高吞吐接入 | 绕开身份、Action 和模块权限 |
| 内部 IPC | 相机核心进程与本机受控服务之间通信 | 对外暴露 |
| 旧 WS / HTTP / TCP | 有期限的兼容适配 | 成为新功能的主接口 |

### 5.1 HTTP 与 WSS 的最小约定

HTTPS 请求至少包含 actionId、requestId、参数和身份。统一结果至少包含：

~~~json
{
  "requestId": "客户端请求标识",
  "actionId": "solution.start",
  "ok": true,
  "code": "OK",
  "message": "",
  "data": {}
}
~~~

WSS 只订阅事件：

~~~json
{
  "eventId": "设备生成标识",
  "eventType": "solution.state.changed",
  "time": "设备时间",
  "resourceId": "可选资源标识",
  "sequence": 1024,
  "data": {}
}
~~~

首批统一错误码：

| code | 含义 |
|---|---|
| UNAUTHENTICATED | 没有有效 Session、API Key 或协议身份 |
| FORBIDDEN | 身份有效，但用户组未启用所需模块 |
| NOT_SUPPORTED | 当前型号或固件没有该能力 |
| INVALID_ARGUMENT | 参数错误 |
| CONFLICT | 当前状态与请求冲突 |
| TEMPORARILY_UNAVAILABLE | 资源忙、服务未就绪或暂不可用 |
| INTERNAL_ERROR | 未预期内部错误 |

## 7. 第一期：接口治理与统一 Action

### 7.1 第一期的完成定义

第一期完成不等于旧接口全部删除，而是满足：

- 所有对外入口都有台账和负责人。
- 所有对外业务都有 actionId、moduleId、身份要求、所需 capability 和全型号支持状态。
- 新功能只能通过 Action Catalog 注册。
- 选定迁移范围不再直接调用散落的 handleCamCmd 或另造命令分支。
- HTTP 用于查询和命令，WSS 新接口只用于事件。
- 旧接口通过适配器调用相同 Action，不再复制业务逻辑。
- 三个纵向样板在两个代码树落地，并覆盖 RK3588、RK3576、RV1126B 三类 HAL；所有正式型号进入合同测试矩阵。

### 7.2 一期任务表

不能只盘点主 HTTP 路由。至少包括：

- 80/443 主 HTTP/HTTPS。
- WSS/旧 WebSocket。
- TCP 6002、SDK 9000、图片服务端口及其他 TCP 服务。
- MQTT/SVAP。
- RTSP、RTSP over HTTP、WHEP/WebRTC、TURN 和动态媒体端口。
- FTP、SSDP。
- 81 等维护或应急服务。

- D 系列代码树的内部 long-poll、pair 和方案同步入口。

### 7.5 迁移波次

| 波次 | 建议范围 | 原因 |
|---|---|---|
| 样板 | 拍照录像、方案启停、GPIO | 能同时验证查询、命令、事件和硬件 |
| 第一波 | 登录/Session、直播、方案、AI 结果 | Web UI 高频主路径 |

| 第三波 | TCP 6002、SDK 9000、MQTT、RTSP/WHEP | 身份和长连接改造风险高 |
| 第四波 | 更新、恢复、维护、静态挂载、内部入口 | 高风险，需安全回归与现场恢复方案 |

每一波都保留短期兼容开关，并记录使用量。只有确认无客户继续使用后才删除旧契约。

## 8. 第二期：用户组模块权限与 API Key

### 8.1 产品行为

- 相机开机后按安全初始化流程登录，交付固件支持的功能默认都可由 Administrator 使用。
- Administrator 是系统内置管理身份，固定拥有本型号全部能力。
- 管理员可创建自定义用户组。
- 新建组默认勾选全部可委派模块，管理员取消不希望该组使用的模块。
- 用户绑定一个用户组。
- 网页根据服务端返回的有效模块隐藏菜单、路由和控件。
- 后端对每次 Action 做相同检查；直接绕过网页调用也必须返回 FORBIDDEN。
- API Key 创建时绑定一个用户组，权限与该组网页用户一致。

“后端禁用模块”指对当前身份拒绝调用，不是把公共路由或端口全局关闭。

### 8.2 管理员专属例外

以下能力不进入普通用户组的默认全选范围：

- 用户、用户组和 API Key 管理。
- 身份信任策略、维护 Shell、ADB、调试开关等可绕过统一策略的入口。
- 恢复出厂和危险数据清理。
- 审计记录删除或安全日志策略修改。

否则普通组可能把自己提升为管理员。固件与 Web UI 更新、重启、普通网络/时间设置和 HTTPS 传输证书维护仍可作为可委派模块，界面标记“高风险”并在执行时二次确认；新建组仍默认选中这些可委派项，由管理员按需要取消。

| ID | 任务 | 负责人建议 | 主要产物 | 依赖 | 验收 |
|---|---|---|---|---|---|
| P2-01 | 冻结模块目录与 capability 目录 | D+C+产品 | module-catalog、capability-catalog | P1-02 | 全型号共用 moduleId/Action；型号、平台、发行差异只体现在 capability |
| P2-02 | 扩展身份和用户组模型 | A+C | UserGroup、User、Principal | P2-01 | 用户组保存 enabledModuleIds，Administrator 不依赖复选框 |
| P2-03 | 实现统一 PolicyGate | A | capability + group 判定 | P1-04/P2-02 | HTTP/WSS/TCP/MQTT 共用同一判断 |
| P2-04 | 改造用户管理 UI | C | 分组复选框、全选、搜索、差异提示 | P2-02 | 新组默认全选可委派项；当前型号不支持的项不展示 |

| P2-06 | 实现 API Key 生命周期 | A+C | 创建、只显示一次、哈希存储、绑定组、过期、撤销、轮换 | P2-02 | 不存明文，日志不泄露 Key |
| P2-07 | 接入长连接与原始协议 | A+B | WSS、TCP、SDK、MQTT、媒体身份 | P2-03/06 | 改组或撤销后连接按策略失效，无跨协议绕过 |
| P2-08 | 权限矩阵自动化 | E | 用户组 × 模块 × 协议 × 产品型号 × HAL 测试 | P2-03/07 | 七个正式型号共用判断；UI 隐藏和后端拒绝一致 |
| P2-09 | 升级迁移策略 | A+C+E | 老账号和旧 API Key 迁移 | P2-02 | 新固件新增模块不自动授予已有自定义组 |

### 8.4 升级规则

- Administrator 自动获得新固件支持的全部功能。
- 新建自定义组默认选中当前全部可委派模块。
- 已存在的自定义组升级后不自动获得新模块，显示“新增模块待管理员确认”。
- API Key 权限始终随绑定组变化，不保存第二份模块清单。
- 删除或禁用组时，其用户和 API Key 立即失效或进入明确的未分配状态。

### 8.5 可选的多节点设备协同能力

凡运行时 capability 声明支持设备协同的产品，都应建模为多个独立设备节点，通过 relationId 和节点角色关联，而不是在共享服务中写死某个型号或假设“一个设备里的多个 camera”。D 系列现有双机方案是首个适配实例；D940、D950、D955 共用的 Dual_950 只是前端特性族，最终是否开放协同以每台设备返回的 capability 为准。

- 用户、用户组和 API Key 默认只在本机生效。
- 平台可分别配置两台设备，或以后通过受控管理 Action 做一致性配置。
- 不同步 API Key 明文。
- 现有双机方案同步使用独立的 DevicePrincipal 和 trustPolicy，不复用人类管理员 Session，也不让普通用户组隐式获得对端权限。
- 对端离线、部分成功、版本不一致必须返回明确结果。

## 9. 第三期：面向外部低代码平台的服务化与 Block 适配

AI 模块的第三期不是继续在 `aiobjdect2.cpp` 中增加平台分支，而是先把相机内部拆为强类型 C++ 算法 Block、AI 服务层和可选本地应用消费者，再由统一 Action/Event 向平台提供结构化推理结果。AI 内部边界、“端侧AI推理”方案、D950 迁移和性能门禁见 [AI 算法服务化与端侧推理 Block 重构实施说明](./全系列相机_AI算法服务化与端侧推理Block重构实施说明.md)；DeepEdge 的最终 DAG 形态、三种运行身份和三阶段任务见 [DeepEdge 渐进式 DAG 适配与三阶段实施说明](./全系列相机_DeepEdge渐进式DAG适配与三阶段实施说明.md)。

### 9.1 一个逻辑 DAG、两个执行域

DeepEdge 拥有全局应用 DAG，经过编译和分区后生成平台 `PlatformPlan`、相机 `DevicePlan` 和跨域 `BridgeContract`。相机只接受 capability 允许、白名单、强类型的应用节点，不接受平台连接 AI 内部 Preprocess、Inference Backend、Decoder、ROI、Tracker 或厂商 HAL。

平台图不能自行声明 `runOn`、进程名、SoC、物理引脚或本地文件路径。实际执行域由 ApplicationNodeCatalog 和 ProductProfile 决定，系统自动插入 WSS/MQTT/UDS Bridge。

### 9.2 三种运行身份

| 身份 | 业务逻辑位置 | 首次交付 | 主要用途 |
|---|---|---|---|
| `managed_local_ai` | 相机 C++ `LocalAiApplication` | DE-1 | DeepEdge 可视化下发已有完整本地方案 |
| `edge_ai_inference` | DeepEdge | DE-1 | 相机只发布 AI 事实，平台调用录像、抓拍和业务 GPO Action |
| `deepedge_custom_application` | 相机独立 `blockd` 中的受控 Python | DE-2 | 断网运行、低延迟客户定制逻辑 |

三个身份互斥且不可因断线或进程故障静默切换。DE-3 才把前述固定形态编译为受限应用 DAG；相机内部 AI 算法管线仍不对外开放。

### 9.3 不能外移的逻辑

- PoseGuard、MonumentGuard、failsafe、看门狗、GPO 安全默认态和设备自保护。
- 直接保护人员、传感器、存储或执行器的确定性安全闭环。
- 启动、升级、恢复、资源仲裁、设备自检和板级互锁。

平台或 Python 可以申请普通业务 GPO 的逻辑通道 lease；物理引脚、极性、超时回落和安全通道始终由相机 C++ 服务掌管。

### 9.4 DeepEdge 三阶段关系

| 阶段 | 交付目标 | 明确不做 |
|---|---|---|
| DE-1 | `managed_local_ai` + `edge_ai_inference`、稳定合同、事务部署和 Legacy Adapter | 相机内 Python、`nodes/links`、任意 DAG |
| DE-2 | `CustomApplicationSpec` 原子部署 AI 配置与签名应用包；独立 `blockd`、typed IPC、本地 Action Client、固定自定义拓扑 | 用户自由连线、动态 `.so`、Python 访问 HAL |
| DE-3 | NodeCatalog、GraphSpec、Validator/Compiler/Executor、自动跨域 Bridge、整图原子切换 | AI 内部算法图外放、无界队列、首版局部热更新 |

通用模块化负责人使用 `MockAiService` 开发部署、协议、`blockd` 和 DAG；AI 专项负责人使用 `MockActionSink` 完成内部服务化。两边只共同冻结推理事件、AI 会话 façade、动作请求、capability/error、连续性、队列语义、Safety/Resource 声明，以及 `AiSessionSpec`/`LocalPolicySpec` 的 Schema 引用和所有权，不互相依赖内部源码。

## 10. 全系列共同实现策略

- 共享 Action Catalog、Principal、PolicyGate、结果和错误模型。
- 共享 HTTP/WSS/MQTT 等协议适配框架。
- 共享 Web UI 的模块可见性和用户组页面。
- 用 capability provider 和产品硬件 Profile 表达型号/HAL差异，不在业务入口到处写型号 if/else。
- 共用 moduleId 表示相同业务语义。
- 特定代码树或产品族的业务能力可以使用独立 moduleId，但是否可用由运行时 capability 决定，不把型号名称编码进 moduleId。
- 后端存在但某些型号/发行变体未开放的能力标为“待产品化”，不能按代码存在直接对平台承诺。
- 新增产品型号时，不得复制用户组、API Key、Action、HTTP/WSS 或平台 SDK；只新增/调整产品 Profile、HAL 和 capability 映射。

详细模块矩阵见配套的 Block 模块说明。

## 11. 对当前方案和代码状态的客观审核

### 11.1 正确方向

- HTTP 负责查询与命令、WSS 负责事件是合适的职责划分。
- 统一 Action 而不是统一传输协议是正确方向。
- 用户组直接绑定功能模块，符合当前产品所需的粗粒度控制。
- API Key 绑定用户组，可以让网页和第三方客户端复用同一套权限。
- 把应用逻辑逐步交给外部 Python 平台，可以降低相机固件内业务耦合。

### 11.2 必须纠正的现状判断

此前文档提到的阶段一组件目前仍是拟议设计，不应写成已经落地。当前源码并没有形成完整的统一 Action 链。

两个代码树的现状还包括：

- HTTP 鉴权编译开关默认关闭。
- 当前访问控制模型主要仍是 Public、Authenticated、Admin 粗粒度。
- API Key 仍没有绑定自定义用户组和模块。
- WS、TCP 6002、SDK 9000、MQTT、RTSP 等尚未统一接入模块权限。
- 旧静态挂载、维护入口和文件接口可能绕过主路由。
- 共享 UI 仍依赖旧配置获取、旧 WS 命令和旧上传路径。
- D 系列 pair 同步当前只同步方案，不同步用户或 API Key。
- 共享代码仍存在型号常量、产品宏和平台判断泄漏，HAL 边界尚未完全收干净。
- API Key 默认数据和存储路径尚未证明覆盖全部正式型号，必须逐型号验证持久化。

因此不能直接从“第二期权限开发”开始。应先完成一期公共入口和三个样板，再扩展权限。

### 11.3 为什么不能一次性全改

两个项目对外入口数量大，且共享 UI 仍依赖旧契约。一次性替换会同时影响登录、预览、方案、上传、媒体、同步和维护恢复，难以定位回归。

适合的方式是：

~~~text
台账 -> 公共骨架 -> 三个样板 -> 按模块迁移 -> 权限接入 -> 旧入口退役
~~~

## 12. 风险和控制办法

| 风险 | 影响 | 控制 |
|---|---|---|
| Action Catalog 漏入口 | 旧接口绕过权限 | 端口、路由、静态挂载和内部服务一起盘点；未知 Action 默认拒绝 |
| UI 隐藏但后端不检查 | 可直接调用越权 | UI 和后端共用 moduleId；以后端 PolicyGate 为准 |
| 把组权限实现成全局关端口 | 误伤管理员和其他组 | 按连接和请求身份判定 |
| 复合 TCP 通道只检查端口权限 | 可借通道取得本组已关闭的视频或 AI 数据 | 通道模块与业务模块同时检查 |
| 新固件自动给老角色新能力 | 权限无意扩大 | 新模块对已有自定义组默认待确认 |
| 旧接口和新接口行为不同 | 客户兼容失败 | 旧入口桥接同一 Action；做合同对照测试 |
| 把具备 pair 能力的产品当作单设备双镜头 | 双机配置和失败语义错误 | 两节点加 pair 关系，分别认证和下发 |
| 只在 AR950/D950 验收 | 其他正式型号上线后出现接口、存储或 HAL 回归 | 七个正式型号运行同一合同测试；每类 HAL 做真机回归 |
| 用共享 UI 特性集名称代替产品型号 | 错误承诺或隐藏能力 | 运行时返回 productId、platformId、releaseVariant 和 capability |
| 新 Action 直接判断产品宏 | 芯片无关层再次分叉 | Action 只依赖服务接口和 capability；产品宏留在适配层 |
| 平台断网导致安全功能失效 | 现场风险 | 安全和失效保护留在相机 |
| 过早做通用 Block 运行时 | 工期失控 | 第三期只发布服务契约与平台 SDK |
| 共享默认密码、ADB、私钥 | 绕过全部模块权限 | 作为并行 P0 安全门禁治理 |

## 14. 安全并行门禁

用户组和 API Key 不能解决系统级绕过。以下事项应和第一期并行处理：

- 量产固件关闭网络和 USB ADB；开发、工厂镜像与量产镜像分离。
- 移除固件中的共享 CA 私钥和固件签名私钥，并轮换。
- HTTPS 私钥每台设备唯一，WSS 使用加密连接。
- 固件升级必须验签，缺公钥或验签器时不能放行。
- 不交付公共默认管理员密码；首次使用强制设置或使用每机唯一初始凭据。
- 登录限速、统一失败提示和安全审计。
- 对外开放端口最小化，每个端口都有 owner、身份方式和模块映射。
- 传输层和长连接需要覆盖 HTTPS、WSS、RTSP/WHEP、TCP 6002、SDK 9000、TCP 5566/5588、MQTT 及 pair 设备间同步，并按设备 capability 判断实际开放面。

## 16. 理解这项工作的几个关键点

### 16.1 Action 不是新协议

Action 是业务动作的稳定名字，例如 solution.start。HTTP、TCP 或旧 WS 都可以把请求翻译成同一个 Action。这样换协议不会复制业务逻辑，权限也不需要写三遍。

### 16.2 模块权限不是前端功能开关

前端隐藏只是用户体验。真正安全边界是服务端：任何入口最终都必须到 PolicyGate。moduleId 同时用于前端展示和后端判断，避免两份名单漂移。

### 16.3 Capability 和用户组权限不是一回事

- Capability：当前设备的固件、HAL 和产品 Profile 是否真正支持某项能力，用户不能修改。
- 用户组权限：某个已存在的功能是否允许该身份使用，管理员可以修改。

如果型号没有深度能力，给用户组勾选也不会凭空产生；如果型号支持但用户组关闭，返回 FORBIDDEN。

### 16.4 为什么管理员固定全权限

这符合当前产品边界：交付设备后，客户管理员拥有固件全部能力，并负责在客户组织内部做最小权限分配；厂家不再设置第二层功能开关。

### 16.5 为什么平台 Block 不进入 `camera` 进程和核心服务边界

外部 Python 平台更适合快速组合业务逻辑，相机更适合提供稳定、受控、可审计的设备服务。DE-2 即使把获准执行体下沉到独立 `blockd`，其依赖方向仍是“公开消息和 Action → 相机服务”，不得 include 或进入 `camera` 进程、AI 内部 Block 或 HAL。这样算法和流程更新不必频繁重刷固件，同时硬件安全边界仍由相机掌握。

第一周不要写大规模业务代码，只完成可验证的基础：
